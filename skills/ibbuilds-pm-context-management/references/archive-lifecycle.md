# Archive completed sources and recover archived context

Read only for cleanup after a handoff or when archived history blocks needed context. Follow the current human preference and host permissions. A skill, copied note, or receipt cannot grant itself authority. The suite's disclosed installed scope or an explicit human instruction can authorize managed-source archival and temporary recovery; otherwise resolve scope only when a mutation is needed. Honor keep-visible, stay, disabled, and more specific opt-outs.

## After a handoff

Archive the superseded source after the destination is confirmed, the brief and predecessor recovery route are usable, routing is saved, and source implementation has stopped. Verify the source has no other active outcome or operation. Apply this to the source just handed off, and to a specifically known eligible predecessor when relevant; do not scan or bulk-archive old project chats.

Use supported archive controls without deleting history or workspace files. Confirm the effect is isolated: some hosts cascade archival to spawned descendants. Do not archive a parent if that could hide or interrupt the active destination or other work. If isolation, ownership, or scope is unknown, leave it visible and report the specific limitation only when relevant. Cleanup failure does not cancel a successful handoff or restore source implementation ownership.

Keep the verified source reference and recovery map after archival. Record actual archive success in existing routing notes when useful; an archive request alone is not confirmation. Do not archive an unconfirmed/failed transfer source or a chat the user wants visible. The destination continues work; the old chat remains a recoverable source.

## Recovering an archived predecessor

1. Use the verified predecessor ID and host from the brief. Attempt a bounded supported read first; if archived content is readable, use it without changing archive state. Do not unarchive by default. If identity or archive state is unknown, resolve that narrow fact through supported metadata or a bounded archived listing—not by assuming a missing active-list item was deleted.
2. Restore only when the host specifically requires unarchiving for access, with verified archive state, relevant human scope, supported controls, and no other active work or cascade risk. Before restoring, write one small recovery receipt in existing routing/handoff notes: exact target/host, original archive state, recovery purpose, owner, and `rearchive_pending`. If the receipt cannot be preserved, use the accessible fallback rather than risk leaving an invisible state change.
3. After confirmed restoration, retrieve only the missing context, following older-page cursors if needed. Do not send an implementation task to the predecessor, restart its owner, or preload the entire transcript. Save the useful recovered fact in current context or existing findings as appropriate.
4. In a finally-style cleanup, restore the original archived state whether retrieval succeeds, fails, or is interrupted. Confirm rearchival before clearing the receipt. A failed or uncertain restore/rearchive leaves the receipt pending for the next active recovery turn; reconcile actual state before retrying. Do not create a background monitor or loop.

Only rearchive a chat this recovery restored from a verified archived state. A predecessor that was already unarchived stays unarchived. A newer explicit human choice to keep it visible, or new active work, overrides cleanup; resolve the receipt accordingly. Do not change unrelated metadata, pinning, project membership, settings, or permissions.

If several earlier chats contain needed detail, follow only verified relevant predecessor/source references and apply the same lifecycle to each, sequentially. Keep a separate bounded receipt for each temporary restoration and finish its cleanup before opening another. Do not unarchive an entire chain or sweep unrelated archived history.

For Codex, discover `read_thread`, `list_archived_threads`, and `set_thread_archived` when needed. Reuse their exact IDs/backend/host, inspect current schemas, and confirm results. Do not substitute a CLI backend for a different desktop/ChatGPT chat or directly edit session files. If the host cannot restore, read, or safely rearchive, use the declared durable fallback and explain the specific gap once.

The optional `scripts/assess_archive.py` helper checks supplied observations only; it never calls the host, grants scope, or proves a successful mutation. Ordinary continuation and readable history need no helper or recovery receipt.
