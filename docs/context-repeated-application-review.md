# Repeated context checks and temporary stays

Version 0.6.12 corrects recurring application guidance, rather than claiming that
installation or a SKILL.md read proves adherence. The observed source chat read
Context Management yet continued substantial work without applying its warning
and continuation procedure. A separate native-discovery audit found all eight PM
and eighteen SWE skills enabled in seven working directories, including skill-
created continuations. Discovery alone did not explain the missed behavior.

## Correction

The entrypoint now distinguishes location choice from notification policy.
An ordinary stay applies to the logical request and related corrections. It does
not create permanent stay/suggest-only/disabled management, suppress reminders
or reset pressure. A new request triggers reassessment. A loaded procedure still
needs its recurring check on substantive turns, after large output and before a
consequential action. Existing measured thresholds, unknown-telemetry safeguards,
explicit lasting opt-outs, transfer authority and safe-checkpoint rules remain.

Request-choice guidance and the continuation template carry the same scope.
The suite's existing optional event reminder now points out recurring application.
A small standalone `turn_reminder.py` offers event-to-pointer delivery for
Context Management without a suite installer receipt or another skill. It reads
only its bounded event input, reflects no user prompt, stores no transcript or
counters, measures no occupancy and never blocks a prompt or creates a chat.
It handles SessionStart and UserPromptSubmit; other events and malformed input
produce an empty successful response.

Actual hook setup remains a separate, concrete, explicitly approved configuration
step. Preserve unrelated hooks and avoid duplicate reminder groups. Trust/reload
through the execution host is required before claiming live delivery. Installing
the skill is not installing or trusting a hook. The reminder provides another
invocation opportunity; it does not guarantee model compliance or measure context.

## Validation and boundaries

An independent fresh executor selected methods from PM descriptions, without
the expected answers or this review. In a fictional multi-turn conversation it:

1. Warned at a supplied fresh 46% observation while providing the requested two steps.
2. Warned at 49% after a request-scoped stay and answered a related clarification.
3. Warned at 56% for a different requested outcome, retaining the old stay's scope.
4. Paused at 63% and prepared a continuation instead of fulfilling a dependent
   follow-up or creating an unauthorized chat.
5. Used a verified fresh-destination 9% observation to complete the comparison
   without importing predecessor notices or counters.

These are synthetic host observations, not actual token measurements or native
host-trigger tests. The policy helper already implemented repeated required
notices correctly; no causal helper repair is claimed. New sequence tests retain
state through stay/refinement/new request/ceiling/recovery and unknown telemetry.
Hook tests execute the standalone command repeatedly and verify output envelopes,
bounded pointers, prompt nonreflection, unrelated-event handling and successful
malformed-input fallback. Suite-hook tests also check that repeated events do not
mutate metadata or store the prompts. Those tests do not establish host scheduling,
trust or model compliance. Existing repository checks and packaging are separate.

Official [OpenAI hooks documentation](https://developers.openai.com/codex/hooks)
was searched and fetched for event input/output and lifecycle/trust behavior.
Installed Codex 0.162.1 can differ from newer documentation; runtime behavior
must be verified in the actual host. No model, sandbox, approval reviewer, telemetry
exporter, private transcript scan or background polling is introduced.
